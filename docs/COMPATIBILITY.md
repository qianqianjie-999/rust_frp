# 兼容性矩阵

本文区分协议兼容、配置兼容和运行环境兼容。三者不能互相替代。

## 版本组合

| 服务端 | 客户端 | 状态 | 说明 |
| --- | --- | --- | --- |
| 旧版 | 旧版 | 已验证 | 原有部署方式 |
| 新版 | 旧版 | 支持 | 旧客户端忽略 `work_conn_port`，通过原有 mux 路径工作 |
| 新版 | 新版 | 支持 | 默认优先使用独立工作端口 |
| 旧版 | 新版 | 设计兼容 | 旧服务端不下发工作端口时，客户端 `auto` 回退 mux |

注意：

- `work_conn_via = "dedicated"` 不能连接未提供工作端口的旧服务端。
- 新版服务端和旧客户端组合仍应执行实际业务验证。
- 版本号 `0.1.0` 不能单独作为兼容性判断依据。

## HTTP 上游

| 场景 | 结论 | 说明 |
| --- | --- | --- |
| Nginx -> HTTP/1.1 -> frps -> frpc -> Nginx/Gunicorn | 推荐 | 双向关闭语义明确 |
| Nginx -> HTTP/1.1 -> frps -> frpc -> Apache/mod_wsgi | 推荐 | 使用 `proxy_http_version 1.1` 后已验证 |
| Nginx -> HTTP/1.0 -> frps -> frpc -> Apache/mod_wsgi | 高风险 | 可能触发长时间半关闭和 504 |
| 纯 TCP，无 HTTP 语义 | 按业务验证 | 仍需覆盖长连接和半关闭 |
| WebSocket | 按业务验证 | 必须覆盖连接复用、断开和重连 |

推荐 Nginx 配置：

```nginx
proxy_http_version 1.1;
proxy_set_header Connection "";
```

不要在没有测试的情况下设置 `Connection: close` 或主动降级 HTTP/1.0。

## 后端框架差异

相同 FRP 版本在不同主机上可能表现不同，原因包括：

- HTTP/1.0 与 HTTP/1.1
- keep-alive 策略
- 后端先关闭读端、写端的顺序
- Gunicorn、Apache/mod_wsgi、Node.js 等框架的连接生命周期
- 代理层是否发送 FIN
- 长连接、上传和 WebSocket 流量比例

因此，一台客户端升级正常，不能证明所有客户端安全。

## wire protocol v2

`transport.wire_protocol = "v2"` 的“默认 v1 行为不变”只说明控制协议编码兼容：

- v2 选项只作用于控制连接。
- 工作连接仍使用 v1 帧格式。
- 该说明不覆盖双端口架构、工作连接生命周期或后端 HTTP 语义。

## 配置兼容

原版 frp 的 camelCase 字段可以解析，但以下情况仍需检查：

- 未知字段在严格模式下会拒绝启动。
- 可以解析的字段不保证与所有业务场景中的预期行为完全一致。
- 日志、TLS、认证和工作连接相关字段应逐项验证。

配置能启动不等于生产兼容。升级验收必须以真实流量为准。
